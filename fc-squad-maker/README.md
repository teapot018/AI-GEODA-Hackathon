# FC 스쿼드 메이커

넥슨 **FC 온라인 Open API** 기반의 구단주 조회 · 선수 검색 · 스쿼드 빌더 · 모의 상자 개봉 시뮬레이터.
Next.js 15 (App Router) + TypeScript + Tailwind CSS.

> 설치 없이 화면만 먼저 보고 싶다면 저장소 루트의 [`demo/index.html`](../demo) 을 브라우저로 열면 됩니다.
> 같은 로직을 서버 없이 도는 한 페이지로 옮긴 판입니다 (넥슨 API 는 호출하지 않고 샘플 데이터를 씁니다).

```
구단주 조회        닉네임 → OUID → 레벨/최고등급/매치기록/거래내역
                   + 최근 20경기 집계 → 승률·득실·선수별 실전 성능
스쿼드 메이커      초성 검색 → 드래그 배치 → 팀컬러·강화 시뮬레이션
                   + 실제 경기 라인업 그대로 가져오기
거래 관측소        조회 가능한 거래 기록 수집 → 카드별 가격대·변동폭·추세
모의 상자 개봉     모의 확률표 → 서버 가중 추첨 → 연출 + 회수율 집계
트레이드 계산기    매입/매도 + 판매 수수료 40% → 실현 손익·손익분기가
```

> **이 프로젝트가 보여 주는 숫자는 세 종류입니다.** 넥슨이 준 값(A), 게임의
> 공식 규칙(B), 이 프로젝트의 추정(C). 셋을 섞지 않는 것이 제1원칙이고,
> 화면에도 색점으로 구분해 붙입니다 — 자세한 것은 [4. 데이터 출처](#4-데이터-출처--무엇이-공식이고-무엇이-추정인가).

## 1. 빠른 시작

```bash
npm install
cp .env.example .env.local     # NX_API_KEY 입력 (없어도 데모 모드로 실행됨)
npm run dev                    # http://localhost:3000
```

| 명령 | 설명 |
| --- | --- |
| `npm run dev` | 개발 서버 |
| `npm run build` | 프로덕션 빌드 |
| `npm start` | 빌드 결과 실행 |
| `npm run typecheck` | 타입 검사 |
| `npm run lint` | ESLint |
| `npm run check:api` | **넥슨 API 점검** — 키가 통하는지, 최신 시즌이 잡히는지 |

### 키를 넣기 전에: `npm run check:api`

키가 실제로 동작하는지, 그리고 **최신 시즌까지 검색되는지**를 앱을 띄우기 전에
확인하는 스크립트입니다. 의존성 없이 Node 만으로 돕니다.

```bash
npm run check:api                                  # .env.local 의 NX_API_KEY 사용
node scripts/check-api.mjs --nickname 내구단주명      # 매치 상세까지 끝까지 조회
node scripts/check-api.mjs --key test_xxx          # 키를 직접 넘겨 확인
node scripts/check-api.mjs --json                  # 결과를 JSON 으로 (CI 용)
```

확인하는 것:

1. **정적 메타** 5종이 열리는가 (인증 불필요)
2. **최신 시즌이 메타에 들어와 있는가** — seasonId 내림차순 상위 8개 시즌과 시즌별 카드 수를 찍어 줍니다.
   여기에 최신 시즌이 보이면 이 앱은 코드 수정 없이 그 시즌까지 검색합니다.
3. **키가 실제로 통하는가** — 넥슨이 돌려준 `OPENAPI000xx` 코드로만 판정합니다.
   프록시가 가로챈 403 처럼 넥슨에 닿지도 못한 응답은 "판정 보류"로 두고 키가 유효하다고 말하지 않습니다.
4. `--nickname` 을 주면 **ouid → 계정정보 → 매치 목록 → 매치 상세 → 출전 선수와 메타 조인**까지 실제로 흘려 봅니다.

종료 코드는 정상 0, 키 불가·메타 접근 실패 1 이라 CI 에 그대로 걸 수 있습니다.

> **테스트 키(`test_`)와 배포 키(`live_`)** — 테스트 키는 유효기간과 호출 한도가 짧습니다.
> 스크립트가 접두사를 보고 경고해 주며, 상시 운영에는 `live_` 키를 발급해 쓰세요.

### API 키 발급

1. <https://openapi.nexon.com> 접속 → 넥슨 계정 로그인
2. 상단 **[APPLICATION]** → **애플리케이션 등록**
3. 게임에서 **FC ONLINE** 선택, 서비스 정보 입력 후 등록
4. 발급된 **api key** 를 `.env.local` 의 `NX_API_KEY` 에 붙여넣기

```env
NX_API_KEY=live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

> **`NEXT_PUBLIC_NX_API_KEY` 는 쓰지 마세요.**
> `NEXT_PUBLIC_` 접두사가 붙은 값은 클라이언트 번들에 **문자열 그대로 인라인**되어
> 배포 즉시 누구나 devtools 에서 꺼내 쓸 수 있습니다. 이 프로젝트는 접두사 없는
> 서버 전용 변수만 사용하고, 브라우저는 항상 자체 `/api/*` 프록시를 거칩니다.
> `src/lib/env.ts` 는 `server-only` 를 import 하므로, 클라이언트 컴포넌트에서
> 실수로 키에 접근하면 **빌드 타임에 에러**가 납니다.

### 데모 모드

키가 없거나 (`FC_ALLOW_MOCK=true`, 기본값) 넥슨 API 호출이 실패하면
닉네임에서 시드를 뽑아 **결정적으로 생성된 목업 데이터**로 화면을 채웁니다.
모든 응답에 `source: "mock"` 이 실리고 UI 에 `데모 데이터` 배지가 뜨므로,
실데이터와 절대 혼동되지 않습니다. 운영에서는 `FC_ALLOW_MOCK=false` 로 두어
실패를 숨기지 않는 편을 권장합니다.

## 3. 사용하는 넥슨 Open API

| 엔드포인트 | 용도 |
| --- | --- |
| `GET /fconline/v1/id` | 닉네임 → OUID |
| `GET /fconline/v1/user/basic` | 닉네임 · 레벨 |
| `GET /fconline/v1/user/maxdivision` | 매치 종류별 역대 최고 등급 |
| `GET /fconline/v1/user/match` | 매치 ID 목록 |
| `GET /fconline/v1/match-detail` | 매치 상세 (스탯 + 출전 선수 11인) |
| `GET /fconline/v1/user/trade` | 이적시장 구매/판매 내역 |
| `GET /static/fconline/meta/spid.json` | 전체 선수 카드 목록 (id, name) |
| `GET /static/fconline/meta/seasonid.json` | 시즌 클래스명 · 아이콘 |
| `GET /static/fconline/meta/spposition.json` | 포지션 코드 |
| `GET /static/fconline/meta/matchtype.json` | 매치 종류 코드 |
| `GET /static/fconline/meta/division.json` | 등급 코드 |

`client.ts` 는 문서화된 오류 코드(`OPENAPI00001`~`OPENAPI00011`)를 한국어 메시지로
변환하고, 429/5xx 에 대해서만 지수 백오프로 재시도합니다.

### 엔드포인트 하나에서 얼마나 뽑아내는가

같은 6개 엔드포인트에서 화면을 몇 개나 만들 수 있는지가 이 프로젝트의 관심사입니다.
**크롤링은 하지 않습니다** — 아래는 전부 공식 API 응답만으로 계산합니다.

| 엔드포인트 | 원래 쓰던 것 | 추가로 뽑아낸 것 |
| --- | --- | --- |
| `/user/trade` | 매입·매도 총액 | `value` 는 그 거래의 체결 금액이다. `offset` 을 밀어 과거까지 모으면 카드별 최저/중앙/최고가, 사분위 흥정 범위, 강화 등급별 가격, 상승·하락 추세가 나온다 → **거래 관측소** |
| `/match-detail` | 골·도움·평점 | 응답에는 그 경기에 뛴 선수들의 슛·패스·드리블·태클·공중볼·카드 스탯이 들어 있다. N경기를 겹치면 승률·득실·점유율·슛정확도·결정력과 **선수별 실전 성능 리포트**가 나온다 |
| `/match-detail` | 출전 명단 표시 | `spPosition` 코드로 **포메이션을 추정**해 실제 스쿼드를 빌더에 올린다. 상대 쪽 스쿼드도 된다 |

#### 이 데이터가 무엇이 **아닌지** 부터

`/user/trade` 는 **전체 이적시장의 전수 거래가 아닙니다.** 현재 Open API 인증
주체에서 조회 가능한 거래 기록이고, 우리가 조회한 구단주가 실제로 사고판 카드만
나옵니다. 그래서 이 프로젝트의 숫자는 "시장에서 3,412건 거래됨" 이 아니라
"우리가 3,412건을 관측함" 입니다 — 화면에도 그 문장을 그대로 띄웁니다
(`market/observations.ts` 의 `TRADE_SAMPLE_DISCLAIMER`).

이어지는 한계도 화면에 적혀 있습니다: **현재 호가가 아니라 과거 거래가**이고,
못 본 거래가 있으므로 건수·빈도는 전부 하한/상한입니다. Open API 는 현재 이적시장
매물을 제공하지 않으므로 호가를 보려면 별도의 수집 인프라가 필요합니다.

`match-detail` 응답이 항상 22명(양 팀 11+11)이라고 **가정하지 않습니다.** 응답이
잘리거나 포지션 코드가 우리 표에 없으면 그보다 적게 오고, 그때 빈 자리를 다른
카드로 메우면 그건 더 이상 그 경기의 스쿼드가 아닙니다. 몇 명을 받아 몇 명을
배치했는지 화면에 적습니다.

`tradeDate` 는 **방향에 따라 가리키는 사건이 다릅니다** — 매입 쪽은 구매 등록,
매도 쪽은 판매 완료입니다. 한 줄로 합쳐 "체결 빈도" 를 내면 아무도 묻지 않은
값이 나오므로, 코드에서 `Observation.timestampMeaning` 으로 구분해 들고 다니고
화면에서도 두 줄로 나눠 적습니다.

## 4. 데이터 출처 — 무엇이 공식이고 무엇이 추정인가

화면 한 줄에 성격이 전혀 다른 숫자가 나란히 뜹니다.

```
손흥민  OVR 121   가치 1,240만 BP   +5 관측가 980만 BP   +5 시 OVR +6
        └ 추정      └ 우리 모델        └ 우리 관측          └ 넥슨 규칙
```

넷 다 그냥 흰 숫자로 뜨면 보는 사람은 전부 "게임에서 온 값" 으로 읽고, 우리
추정치로 실제 거래를 합니다. 그래서 네 계층을 정의하고(`data/provenance.ts`)
숫자 옆에 색점으로 붙입니다.

| | 계층 | 뜻 | 어디 |
| --- | --- | --- | --- |
| 🟢 | **공식 API** | 넥슨 Open API 응답값 그대로 | `nexon/types.ts` |
| 🔵 | **공식 규칙** | 넥슨이 공지·공개한 게임 규칙 | `fconline/rules.ts` |
| 🟡 | **관측 표본** | 우리가 조회로 모은 거래 기록. 사실이되 표본 | `market/observations.ts` |
| ⚪ | **프로젝트 추정** | 이 프로젝트가 계산한 값. 게임의 수치가 아님 | `players/value.ts` 등 |

### 🟢 넥슨 공식 API

OUID · 닉네임 · 레벨 · 매치 종류별 역대 최고 등급 · 매치 기록 · 매치 상세 스탯 ·
출전 선수 spid · 거래 기록 · **선수 카드 목록과 시즌 메타**.

등급은 **매치 종류마다 사다리가 따로**라 종류를 가로질러 "역대 최고" 하나를
뽑지 않습니다. 대표값은 공식경기로 고정하고 어느 종류의 등급인지 라벨에 적습니다.

### 🔵 FC 온라인 공식 규칙 — `fconline/rules.ts` 한 파일

| 항목 | 값 |
| --- | --- |
| 강화 단계 | **+1 ~ +13** (2024 겨울 업데이트로 +11~+13 추가) |
| 강화 누적 오버롤 상승 | +1 부터 `0, 1, 2, 4, 6, 8, 11, 15, 17, 19, 21, 24, 27` |
| 이적시장 판매 수수료 | **40%** (판매자에게만) |
| 수수료 감면 | PC방 30% + TOP CLASS 20%, **더해서** 적용 (곱이 아님) |
| 데이터센터 기준가 집계 주기 | 2시간 (집계 주기이지 갱신 *시각* 이 아님) |

같은 숫자를 두 곳에 적어 두면 게임이 규칙을 바꿨을 때 한쪽만 고쳐지고 화면마다
다른 말을 하게 되므로, 이 파일 하나만 고치면 되도록 모았습니다.

### ⚪ 자체 추정 모델 (공개 API 에 없음)

| 항목 | 어디서 오나 | 파일 |
| --- | --- | --- |
| 능력치 · 오버롤 | 로컬 시드 64명, 없으면 포지션 기반 추정 | `players/dataset.ts`, `players/estimate.ts` |
| 시즌 티어 보정 | className 키워드 매칭 (ICON/TC/UP …) | `players/seasons.ts` |
| BP 가치 | 오버롤 지수곡선 × 시즌 배수 × 강화 배수 | `players/value.ts` |
| 강화 성공률 | 근사 테이블 (공지 확인 범위 밖) | `players/enhance.ts` |
| 팀컬러 | 같은 클럽/국가/리그 인원수 임계치 | `squad/chemistry.ts` |
| 포메이션 | `spPosition` 구성에 가장 잘 맞는 것을 고른 값 + 일치도 | `squad/import.ts` |
| 상자 이름 · 가격 · 확률 | **전부 이 프로젝트가 만든 모의 값** | `pack/boxes.ts` |

**시드 프로필도 추정입니다.** `players/dataset.ts` 는 사람이 손으로 적어 넣은
표이고 게임 화면과 대조해 검증한 적이 없습니다 — 손으로 적었다고 공식이 되지
않으므로 `statSource` 는 `project-seed` / `project-formula` 둘 다 `project-` 로
시작하고, 카드에는 어느 쪽이든 `추정` 배지가 붙습니다.

**카드의 존재 여부는 시드가 정하지 않습니다.** 카탈로그는 넥슨 `spid.json` 이 준
목록으로만 만들어지고 시드는 그 카드를 꾸밀 뿐입니다. 다만 넥슨 메타를 받지 못해
**데모 카탈로그**로 떨어지면 spid 를 이름 해시로 만들어 내므로, 그때 뜨는 카드
조합은 실제 게임에 있다는 보장이 없습니다 — 그 경우 선수 검색에 경고가 뜹니다.

**보유 자산(BP/캐시 잔액)은 Open API 가 제공하지 않습니다.** 그래서 자산 패널은
잔액 대신 최근 거래 기록으로 계산한 **자금 흐름**(매입/매도/순손익)을 보여주고,
헤더에 `잔액 아님` 을 명시합니다.

### 공식 데이터로 교체하기

설계상 갈아끼우는 지점이 파일 하나씩으로 고정되어 있습니다.

- **능력치 DB** → `players/dataset.ts` 를 자체 DB 로 교체.
  조인 키는 **선수 이름**(`spid.json` 의 한글 표기)이라 나머지 코드는 그대로입니다.
- **가치 모델** → `players/value.ts` 의 `estimateValue()` 만 교체.
- **공시 확률** → `pack/boxes.ts` 의 `tiers[].probability` 를 게임 내
  &lsquo;확률 공개&rsquo; 표 값으로 바꾸고, **같은 줄의 `probabilitySource` 를
  `'official'` 로** 고칩니다. 값만 바꾸면 화면은 여전히 표본이라 적고, 필드만
  바꾸면 표본을 공식이라 부르게 됩니다. `validateBox()` 가 합계 100% 를 검증합니다.

### 데이터가 언제 것인가 (갱신 주기)

이 앱이 보여 주는 값은 대부분 &lsquo;지금&rsquo;이 아닙니다. 가격은 과거 거래가고,
전적은 이미 끝난 경기입니다. 그래서 숫자 옆에 **언제 것인지**를 항상 같이 띄웁니다
(`components/ui/FreshnessNote.tsx`).

| 항목 | 주기·지연 |
| --- | --- |
| 넥슨 데이터센터 **기준가** 집계 | **2시간** 주기. 집계 후 홈페이지 반영까지 추가 지연이 있고, 선수마다 갱신 시점이 달라 게임 내 기준가와 완전히 일치하지는 않습니다 |
| `/user/trade` **거래 기록** | 집계값이 아니라 거래 원본이라 고정 주기가 없습니다. 신선도는 표본의 최신 거래 시각으로 잽니다 |
| `/match-detail` **경기 기록** | 즉시 반영되지 않습니다. 직전 경기는 아직 안 보일 수 있습니다 |
| 관측 **보관 기한** | **30일** 이 지난 관측은 지수에서 뺍니다. 이 숫자는 **이 프로젝트가 정한 정책값**입니다 — 넥슨 이용약관이 며칠을 요구하는지는 확인하지 못했으므로 약관상 의무라고 적지 않습니다 |

신선도 눈금은 기준가 주기(2시간)에 맞췄습니다 — 최신 관측이 2시간 안쪽이면
게임 내 기준가와 대체로 같은 시대를 보고 있는 셈이고, 하루가 넘어가면 다른
이야기이기 때문입니다.

| 배지 | 조건 |
| --- | --- |
| 최신 | 2시간 이내 |
| 양호 | 12시간 이내 |
| 조금 지남 | 24시간 이내 |
| 오래됨 | 그 이상 |

> **시각은 UTC 로 옵니다.** Open API 는 `2024-06-01T12:34:56` 처럼 타임존이 없는
> 문자열을 주는데 이 값은 UTC 기준입니다. 그냥 `new Date()` 에 넣으면 실행 환경의
> 로컬 시간으로 해석돼 한국에서 9시간이 어긋납니다. `parseApiDate()` 가 `Z` 를
> 붙여 UTC 로 못박고, 표시할 때 `Asia/Seoul` 로 변환합니다.

&lsquo;다음 집계 예상&rsquo;은 2시간 주기를 정각 기준으로 올림한 **어림값**입니다.
넥슨이 정확히 몇 분에 도는지는 공개돼 있지 않아 화면에도 &lsquo;예상&rsquo;이라고 적었습니다.

### 누적 관측 풀 — 표본을 넓히는 유일하게 정당한 방법

**Open API 에는 호가(현재 매물가) 엔드포인트가 없습니다.** 지금 이적시장에 얼마짜리
매물이 걸려 있는지는 공식 API 로 알 수 없고, 알아내려면 로그인 세션이 필요한 게임
클라이언트나 웹 이적시장을 긁어야 합니다. 이 프로젝트는 그 선을 넘지 않습니다
(계정 정지 사유이기도 합니다).

다만 **`/user/trade` 가 주는 값은 추정가가 아니라 실제로 거래된 금액**입니다.
다른 가격 사이트와의 차이는 값이 진짜냐가 아니라 **표본이 얼마나 넓으냐**였습니다.
그래서 조회할 때마다 거래 기록을 프로세스 메모리 풀에 합쳐, 조회가 누적될수록
카드 커버리지가 넓어지게 했습니다 (`market/pool.ts`, `market/livefeed.ts`).

풀이 넓어져도 **전수가 되지는 않습니다.** 조회하지 않은 구단주의 거래는 영원히
들어오지 않으므로, 이 지수는 끝까지 표본입니다.

| | 1회 조회 | 2회 | 3회 |
| --- | --- | --- | --- |
| 누적 관측 | 200건 | 400건 | 600건 |
| 카드 종수 | 23종 | 45종 | 64종 |

같은 거래가 다시 들어오면 `side:saleSn:spid` 키로 걸러 표본이 부풀지 않습니다.
갱신 때마다 직전 스냅샷과 비교해 **움직인 카드**를 함께 보여 줍니다.

- **약관을 코드로 강제합니다.** 보관 기한 30일(`RETENTION_DAYS`)이 지난 관측은
  조회할 때마다 반드시 떨어집니다 — &lsquo;언젠가 지우겠다&rsquo;가 아니라 읽을 때마다
  걸리는 규칙이어야 지켜집니다.
- **풀은 프로세스 메모리입니다.** 서버리스에서는 인스턴스가 재활용되면 비워지고,
  인스턴스가 여러 개면 각자 다른 풀을 봅니다. 그게 정상 동작이며 화면에도 적어
  뒀습니다. 영구 저장이 필요하면 `pool.ts` 의 `absorb`/`read` 두 함수만 KV·DB 로
  갈아끼우면 됩니다.

#### 표본 범위 (`scope`)

풀을 만들어 놓고도 한동안 **가격표는 이번 조회분만** 쓰고 있었습니다. 풀은 통계
패널과 변동 카드에만 반영돼, "조회할수록 가격 분포가 촘촘해진다" 는 화면의 약속을
정작 가격표가 지키지 않았습니다. 표본 범위를 고를 수 있게 고쳤습니다.

| `scope` | 가격표 표본 | 성격 |
| --- | --- | --- |
| `pool` (기본) | 그동안 쌓인 관측 전체 | 표본이 넓어 중앙값·사분위가 안정적 |
| `account` | 이번에 조회한 계정의 거래만 | 표본은 얕지만 출처가 분명 |

기본값이 `pool` 인 이유는 **가격이 계정이 아니라 시장의 속성**이기 때문입니다.
실제로 벌어지는 폭 (데모 데이터, 조회를 거듭하며 측정):

| 조회 | `account` | `pool` |
| --- | --- | --- |
| 1회 | 23종 | 23종 |
| 2회 | 24종 | **45종** |
| 3회 | 23종 | **64종** |

다만 위쪽 **매입·매도 총액 타일은 언제나 `account`** 입니다. 그건 가격이 아니라
그 계정의 현금 흐름이라, 다른 계정 관측을 섞으면 뜻이 달라집니다.

### 넥슨 공시 기준가 대조 (`market/datacenter.ts`)

관측 가격 옆에 **넥슨이 2시간 주기로 집계·공시하는 기준가**를 나란히 놓고 비교합니다.

| | 출처 | 성격 | 커버리지 |
| --- | --- | --- | --- |
| **관측 거래가** | `/user/trade` | 조회 가능한 거래 기록 | 조회한 계정 (풀로 누적) |
| **기준가** | 데이터센터 공개 페이지 | 2시간 집계값 | 전 카드 |

둘은 서로를 **대체하지 않습니다.** 어긋나는 폭 자체가 정보입니다 — 관측 거래가가 기준가보다
계속 높다면 그 카드는 지금 기준가로는 못 산다는 뜻입니다.

- 로그인 없이 열리는 **공개 페이지**만 읽습니다. 실시간 호가가 있는 이적시장은 로그인
  세션 안에 있고 계정 정지 사유라 건드리지 않습니다.
- **자동으로 훑지 않습니다.** 카드마다 페이지를 한 번씩 부르는 구조라, 사용자가 특정
  카드를 펼치고 버튼을 눌렀을 때만 1회 호출합니다.
- 실패해도 throw 하지 않습니다. 기준가는 관측 가격을 보조하는 참고치라, 못 가져왔다고
  화면이 비면 안 됩니다.

#### 파서가 여러 전략을 쓰는 이유

이 어댑터는 **실제 응답을 한 번도 보지 못한 채 작성됐습니다.** 개발 환경에서 넥슨
도메인이 막혀 있었기 때문입니다. 그래서 파서를 하나로 확정하지 않고 네 전략을 순서대로
시도하며, 어떤 전략이 걸렸는지(`strategy`)를 결과에 담습니다 — 구조가 바뀌어 실패해도
&lsquo;왜&rsquo;가 남아야 고칠 수 있습니다.

```
embedded-json  →  data-attribute  →  price-class  →  bp-label
(정확한 것부터)                                      (최후 수단)
```

실제 구조는 이 스크립트로 확인합니다:

```bash
npm run probe:datacenter                    # 기본 카드로 점검
npm run probe:datacenter -- --spid 300235494 --grade 5
npm run probe:datacenter -- --dump page.html   # HTML 저장
```

파서가 통하면 인식한 가격과 전략을 알려 주고, 실패하면 **가격처럼 생긴 숫자 주변 구조와
XHR 후보 URL** 을 뽑아 줍니다.

#### 코드를 안 고치고 직접 맞추기

구조를 확인했으면 환경 변수 한 줄로 바로 맞출 수 있습니다. 이 패턴은 내장 전략보다
**먼저** 시도되며, 첫 캡처 그룹이 가격입니다.

```bash
# .env.local
FC_DATACENTER_PRICE_PATTERN=class="price_now">([\d,]+)
```

넥슨이 구조를 바꿀 때마다 코드를 고치고 배포하길 기다릴 필요가 없도록 둔 탈출구입니다.
잘못된 정규식은 조용히 무시되고 내장 전략으로 넘어갑니다 — 패턴 하나 때문에 조회가
통째로 죽으면 안 되니까요.

### 알려진 한계

- **데이터센터 파서는 실제 페이지로 검증되지 않았습니다** (`PARSER_VERIFIED = false`).
  이 개발 환경의 이그레스 정책이 넥슨 도메인을 막아(CONNECT 403) 실제 HTML 을 한 번도
  열지 못했고, 단위 테스트는 우리가 만든 가짜 HTML 로만 돕니다. 검증 안 된 정규식은
  가격이 아닌 옆 칸 숫자도 똑같이 잡아 오므로, 화면의 기준가 옆에 그 사실을 적습니다.
- 데모 모드의 카드 풀은 시드 64명 × 8시즌 = 512장뿐이라 등급 분포가 상위에 쏠립니다
  (`레전드` 풀이 `에픽` 풀보다 큰 역전이 보일 수 있음). 실제 `spid.json` 을 받아오면
  2만 장 이상으로 정상화됩니다. 풀 크기는 확률표에 그대로 노출됩니다.
- 팀컬러는 넥슨이 정의한 고정 조합 목록이 아니라 인원수 기반 근사입니다.
- 매치 상세는 건당 1콜이라, 목록에서 펼칠 때만 호출합니다(호출량 절약).
- 랭커 API(`/ranker/*`)는 **있지만 쓰지 않습니다**(`NX_UNUSED`). 화면에 랭킹이 없는
  것이 "API 가 안 준다" 로 오해되면 다음 사람이 없는 데이터를 추정으로 메우게 되므로,
  안 쓴다는 사실을 코드에 적어 둡니다.

## 5. 주요 구현 노트

### 초성 검색

완성형 한글의 유니코드 배열(`0xAC00 + (초성×21 + 중성)×28 + 종성`)을 역산해
초성 키를 만들어 둡니다. 질의가 자음으로만 이루어지면 초성 키에, 아니면 이름에
매칭하고 점수(완전일치 100 / 접두 85 / 포함 60)로 정렬합니다.

```
"ㅅㅎㅁ" → 손흥민     "ㄱㅁㅈ" → 김민재     "음바페" → 음바페
```

쌍자음은 단자음으로 접어(`ㄲ→ㄱ`) 오타에도 걸립니다. → `utils/hangul.ts`

### 스쿼드 배치

- **드래그**: 검색 카드 → 피치 슬롯 (`application/x-fc-card`),
  슬롯 → 슬롯 스왑 (`application/x-fc-slot`)
- **클릭**: 빈 슬롯 선택 후 검색 결과 클릭
- **자동 배치**: 현재 검색 결과에서 `오버롤 × 포지션 적합도` 최대인 선수로 빈 자리 채움
- 포메이션을 바꾸면 기존 선수를 적합도 기준으로 새 슬롯에 재배치
- 상태는 zustand + localStorage 에 저장 → `squad/store.ts`

### 상자 추첨

추첨은 **서버에서만** 합니다. 클라이언트에서 뽑으면 확률표가 번들에 노출되고
결과 조작이 가능해 시뮬레이터로서의 신뢰가 떨어지기 때문입니다.

- 가중 추첨은 누적합 + 이진 탐색 `O(log n)` → `utils/rng.ts`
- `mulberry32` 시드 PRNG — 같은 시드는 같은 결과 (결과 공유·확률 검증에 사용)
- 천장(pity): 클라이언트가 카운터를 누적해 보내면 서버가 확정 등급으로 전환
- 등급 풀이 비면 확률이 재분배되므로 `console.warn` 으로 경고

검증 결과 (3,600장 표본, `premium-bp`):

| 등급 | 공시 | 실측 |
| --- | --- | --- |
| common | 62.000% | 62.806% |
| rare | 27.000% | 26.333% |
| epic | 9.300% | 8.944% |
| legend | 1.600% | 1.861% |
| icon | 0.100% | 0.056% |

### 왜 `security.test.ts` 가 있는가

이 프로젝트에서 되돌릴 수 없는 사고는 하나뿐이다 — 넥슨 API 키가 클라이언트
번들에 박혀 배포되는 것. 한 번 나가면 회수가 안 되고 키를 폐기·재발급하는 수밖에
없다. 그래서 리뷰에 맡기지 않고 소스 트리를 직접 훑는다.

- `process.env.NEXT_PUBLIC_*` 를 읽는 파일이 있으면 실패
- `NX_API_KEY` 를 `src/lib/env.ts` 밖에서 읽으면 실패
- `'use client'` 파일에서 import 그래프를 따라가 `server-only` 모듈에 닿으면 실패
  (타입 전용 import 는 컴파일 때 지워지므로 제외한다)
- 키처럼 생긴 문자열이 소스에 박혀 있으면 실패

실패 시에는 `AssetPanel.tsx → service.ts → env.ts` 처럼 **경로를 그대로 출력**한다.

### CI

`.github/workflows/ci.yml` 이 푸시·PR 마다 네 가지를 순서대로 돌린다:
타입체크 → 린트 → 테스트 → 프로덕션 빌드. 빌드는 `NX_API_KEY` 를 비운 채로
돌려서, 키가 없는 기여자도 저장소를 받아 바로 빌드할 수 있음을 보장한다.

## 8. 배포 (Vercel)

이 앱은 리포지토리 루트가 아니라 **`fc-squad-maker/` 하위**에 있다. Vercel 은 기본적으로
리포지토리 루트에서 `package.json` 을 찾으므로, 아무 설정 없이 연결하면 빌드 대상을
찾지 못하고 실패한다.

### Root Directory 설정 — 이것 하나면 된다

Vercel 이 `fc-squad-maker` 를 프로젝트 루트로 취급하게 만든다. Next.js 자동 감지와
서버리스 함수 경로가 전부 정상으로 잡힌다.

- **새로 연결**: [vercel.com/new](https://vercel.com/new) → 리포지토리 Import →
  *Configure Project* 에서 **Root Directory → Edit → `fc-squad-maker`** → Deploy
- **이미 연결돼 실패 중**: **Settings → General → Root Directory** 에 `fc-squad-maker`
  입력 → Save → **Deployments → ⋯ → Redeploy**

이후는 Vercel 이 알아서 설치·빌드한다. **`vercel.json` 은 필요 없다.**

### 루트에 `vercel.json` 을 두지 말 것

한때 대시보드를 못 건드리는 경우를 대비해 리포지토리 루트에 이런 파일을 뒀었다:

```json
{
  "installCommand": "cd fc-squad-maker && npm ci",
  "buildCommand": "cd fc-squad-maker && npm run build",
  "outputDirectory": "fc-squad-maker/.next"
}
```

Root Directory 가 루트일 때는 이게 맞지만, **Root Directory 까지 설정하면 두 개가
겹쳐서 깨진다.** Vercel 이 이미 `fc-squad-maker` 안에서 명령을 실행하는데 거기서
또 `cd fc-squad-maker` 를 하니 `fc-squad-maker/fc-squad-maker` 를 찾다 실패한다.

증상이 특이해서 적어 둔다 — **2초 만에 실패하고 빌드 로그에 npm 출력이 한 줄도 없다.**
`npm ci` 가 실패한 게 아니라 그 앞의 `cd` 에서 죽기 때문이다.

```
Command "cd fc-squad-maker && npm ci" exited with 1
```

실제로 이 리포지토리에서 겪었고, 그래서 그 파일을 지웠다.

### 환경 변수

**변수를 하나도 넣지 않아도 배포는 성공하고 화면도 뜬다** — 키가 없으면 `FC_ALLOW_MOCK`
기본값(`true`)에 따라 데모 데이터로 동작하고 헤더에 "데모 모드" 배지가 붙는다.
실데이터를 붙이려면 **Settings → Environment Variables** 에 7절의 변수를 넣고
**Redeploy** 한다. `NEXT_PUBLIC_` 접두사는 절대 붙이지 않는다 (7절 참고).

배포 후 `/api/health` 를 열면 키 인식 여부(`apiKeyConfigured`)와 메타 출처
(`metaSource`)를 확인할 수 있다.

## 9. 고지

넥슨 FC 온라인 Open API 를 이용한 **비공식 팬 프로젝트**입니다.

상자 개봉은 실제 결제·아이템 획득과 무관한 **시뮬레이션**입니다. 여기 상자는 FC
온라인 확률표를 참고해 만든 **모의 상자**이며 이름·가격·확률 모두 이 프로젝트가
정한 값이라 실제 상품과 다릅니다. 실제 확률은 게임 내 &lsquo;확률 공개&rsquo;
페이지의 공시를 확인하세요.

거래 가격은 **전체 이적시장의 전수 데이터가 아니라** 현재 Open API 인증 주체에서
조회 가능한 거래 기록을 누적한 **관측 표본**입니다. 오버롤·능력치·가치는 공개
API 에 없는 항목이라 이 프로젝트가 추정한 값이며, 게임에 뜨는 숫자가 아닙니다.

### 확인하지 못한 것

이 환경에서는 넥슨 도메인(`open.api.nexon.com`, `fconline.nexon.com`)이 이그레스
정책에 막혀 있어(CONNECT 403), 아래는 **원문 대조를 하지 못했습니다.**

| 항목 | 상태 |
| --- | --- |
| 강화 오버롤 상승표 | 공지 원문 미대조 — 커뮤니티 정리표와 교차 확인만 함 |
| `/user/trade` 가 정확히 누구의 거래인가 | **확인 불가** — "현재 인증 주체에서 조회 가능한 기록" 이라는, 어느 해석에서도 참인 표현을 씁니다 |
| 데이터센터 페이지 구조 | **미검증** — `PARSER_VERIFIED = false` |
| 이용약관의 데이터 보관 규정 | **확인 불가** — 30일은 이 프로젝트의 정책값 |
| 강화 성공률 | **추정** — 12→13 이 1% 라는 것 외에는 근사표 |
